🧩 Problem

Agents in n8n today are one-shot — they run when triggered, hold no state across time, and can't pursue a multi-step goal to completion. Community users hit this ceiling when they try to build agents that pursue outcomes over hours or days, and either fall back to workflow patterns stitched together with manual "wait" nodes, or go to competitors that already support this.

🧪 Hypothesis

By giving agents a state substrate, goal/plan tracking, and execution mechanics (checkpointing, resume, clean termination on completion or cost cap), we can let agents pursue a goal across time and survive interruptions — driving community adoption of goal-based agents.

Source: Notion — "Long-running goal-based agents" (Agents team, Q3 2026 roadmap)

What is a long-running task?

Simple test: is the agent just running a fixed script when something triggers it, or is it actually chasing an open goal it has to keep judging its own progress on?

What it is
  • Waits in between — short bursts of work, waiting on a person or event in between. Takes a long time overall, but the agent isn't actually busy most of that time. Example: a support-triage agent sitting on a channel for days.
  • Working non-stop — lots of steps back to back, no waiting, genuinely busy the whole way through. Example: deep research, or "find 500 leads and add the good fits to HubSpot."
What it is not
  • Short, scheduled or triggered — nothing to wait for. Example: today's Slack Agents Digest — checks hourly, posts or stays quiet. Looks like monitoring, but it's really just a fixed routine, not a real goal.

How this works, in a nutshell

Before the roles, the risk rules, and the screens below — the whole thing as a flow.

1
Identify & plan
Set up ahead of time by the author, or spotted on the fly when a request is too big for one reply — either way, the agent puts together a plan and shows it, skipped for simple, obviously-scoped prompts.
→
2
Approve
In chat, you approve the plan before it starts. Triggered any other way — schedule, API, Slack — it skips that and only asks when something risky comes up.
→
3
Work it
Check in, pause, edit, or leave it running in the background — anything genuinely risky still gets a check with you first, unless the author already said not to ask.
→
4
Done, plainly
Eventually it finishes, and tells you plainly what it did.

Author vs. consumer — who can do what

Follows Design principle #1 and #2 above: the author defines the ceiling and the risk categories once; the consumer operates a session within them.

Author can

Builds and owns the agent — configures it, sets its limits, and can also use it like a consumer would.

  • Turn on Long-running task mode for the agent at build time (the explicit path)
  • Define which actions count as low-risk vs. high-risk for this agent
  • Set the cost cap (overall and per session) and the autonomy ceiling
  • Edit the agent's plan-generation instructions
  • Choose the default approval-channel routing
  • Test the agent themselves via Preview — acting as a consumer would, but with full configuration rights
  • View the trace/progress of any session
Not in MVP
  • Grant or withhold auto-mode for consumers, up to the ceiling they define
Consumer can

Uses an already-published agent — triggers and steers a session, but never past what the author configured.

  • Trigger a long-running task, explicit or implicit, within what the author published
  • Start the generated plan for their own session
  • Request plan changes conversationally (re-plan via feedback) — not structurally edit it
  • Pause, resume, or cancel their own session
  • Choose to be more conservative than the author's default (ask about more things) — never more permissive
  • View the trace/progress of their own session

Autonomy and risk

Two halves of one model: the rules (Design principles) and what they mean concretely in n8n (Risky vs. not risky, below) — read together, not as separate topics.

🛡 Design principles

Ground rules for every decision below — referenced rather than re-argued each time a screen or setting touches autonomy or risk.

  1. A consumer session can never exceed the autonomy ceiling the author configured for risky actions — it can only be more conservative (ask about more things), never more permissive.
  2. What counts as low-risk vs. high-risk for a given agent is defined once by the author, at build time — not something each consumer configures per session.
  3. Non-chat/async invocation paths (schedule, workflow, API) default to per-tool approval. Full autonomy on these paths is an explicit, author-granted exception, never a silent default.
  4. Some actions stay gated no matter what mode or ceiling is active — real spend beyond the cap, and irreversible external actions (see "Risky vs. not risky" below).

Risky vs. not risky, in n8n

Grounds Design principle #2 and #4 in concrete n8n actions, not abstract risk levels.

Not risky — safe to pre-approve
  • Reading or searching data (CRM lookup, database read, workflow read)
  • Searching the web
  • Reading or summarizing files
  • Drafting a message or report without sending or publishing it
  • Checking the status of a system
  • Internal calculations or analysis
Risky — always confirm, or capped by the author's ceiling

Not risky as a manual n8n action — sending a Slack message is completely routine when a person or a configured workflow does it. It's risky specifically when the agent decides on its own, mid-run, to do it.

  • Sending a message externally (Slack, email, SMS) to a real recipient, on the agent's own judgment
  • Executing a payment or financial transaction
  • Deleting or overwriting production data
  • Publishing or deploying a workflow or agent
  • Modifying a live credential, webhook, or integration
  • Calling a third-party API with a real side effect (creating a ticket, canceling a subscription, updating a customer record)
  • Posting publicly

MVP decisions

  1. 1The plan is generated and surfaced by default; approval is required to start, for the chat-invoked path.Source: comment thread, Aug 28
  2. 2Non-chat/async invocation (workflow, API, cron) proceeds straight to execution with per-tool HITL instead of an upfront plan approval — already the flow above.
  3. 3Plan changes happen conversationally — user gives feedback in a textarea, the agent re-plans and re-shows it — not through a separate structured plan editor.Source: comment thread, Aug 28
  4. 4Progress shows as step-based framing ("3 of 7 steps"), not a calendar-time estimate — agents can't reliably predict duration.Source: comment thread, Aug 28 (rejects the literal hours/weeks ask)
  5. 5Approval granularity ships as four primitives: Approve all always / Approve once / Cancel / Per tool.Source: comment thread, Aug 28
  6. 6Those primitives are bundled into a few named presets for the author (e.g. "Ask before everything" / "Ask only for risky actions" / "Don't ask, just notify"), with per-tool as an advanced option — not a flat grid by default.
  7. 7Cost cap exists at both agent level (overall) and session level; author-only editable, with a notify-me option.Source: comment thread, Aug 28
  8. 8Approval defaults to the channel the task was triggered in.Source: comment thread, Aug 28
  9. 9Short and long-running tasks get distinct visual treatment — a persistent status pill for the long-running one vs. an ephemeral indicator for a short reply.Source: comment thread, Aug 28
  10. 10Status states cover at least: running, paused, completed.Source: comment thread, Aug 28
  11. 11Users can pause and resume a long-running task. Kept even though no major competitor researched ships true pause-and-resume of a single in-flight run — the Needs-approval case is why it still earns its place: other subtasks can be genuinely running in parallel while one thing is blocked on approval, so pausing everything is a real, distinct action from approving or rejecting that one item. Resolves former Open question #6.Source: comment thread, Aug 28
  12. 12The agent stays conversationally available for quick questions while a long-running task executes in the background — the chat input isn't locked to the long-running session.Source: viewer 6966e30d
  13. 13Tool-call/error visibility reuses the existing Trace view, extended with the long-running-specific elements already sketched (goal header, subtask groups) — not a new surface built from scratch.Source: comment thread, Aug 28
  14. 14"Invoke via chat" is dropped as a separate concept; both flow-diagram branches use the same "Preview" label.Source: comment thread, Aug 28
  15. 15The consumer can request plan changes conversationally, same mechanism as the author (Decision #3) — not an author-only capability. Resolves former Open question #6.

Not in MVP

  1. 1Per-channel cost cap granularity (e.g. different caps for Slack vs. Web vs. Telegram) — agent- and session-level caps cover the common case for now.Source: comment thread, Aug 28
  2. 2Consumer-level auto-mode and its guardrails — what happens if a consumer wants zero interruptions, and what the cost implications are. Real question, deferred until the core approval loop (MVP decisions above) is proven.Source: comment thread, Aug 28
  3. 3Configurable approval-channel override — routing approvals to a channel different from where the task was triggered (e.g. running on web, approving via Slack).Source: comment thread, Aug 28
  4. 4Multiple concurrent long-running sessions for the same agent and channel, from different users — not the main use case per the original scoping note.
  5. 5The hardest use-case cell from the map above — consumer, implicit trigger, async/no-one-present — needs the consumer auto-mode and guardrail work (item 2) resolved first.
  6. 6Actual default values for the Settings screen (which options are pre-selected, what the edit-icon modal contains) — the mechanism is scoped, the specific defaults aren't chosen yet.Source: comment thread, Aug 28
  7. 7A fully explicit "Don't ask me anything" option distinct from "Approve all always" — revisit once real usage shows the existing primitive isn't enough.Source: comment thread, Aug 28

Open questions

  1. 1Why is the main use case framed around Preview rather than Agent builder — is it really "build a complex agent" vs. "execute a complex agent," and does that split hold up?Source: raised on the FigJam board, not yet answered in the Notion PRD
  2. 2Can a user have multiple goals / sessions running at once, and if so, is that a single composite goal decomposed into sub-goals, or genuinely parallel sessions?Source: raised in Notion PRD comments
  3. 3Does Slack (or any channel medium) get an explicit trigger at all, given it has no textarea mode picker — or is it implicit-only there?
  4. 4Is the explicit "Long-running task" picker actually needed, or could we rely entirely on the agent detecting goal complexity and proposing it itself? The explicit option adds a second path to design and maintain — worth it only if it's doing a real job beyond letting users discover the capability exists. Is discoverability itself that job, or is there more to it?
  5. 5Could the graph/canvas view (screen 7, currently "vision, not P0") actually be the release UI instead of the timeline + session list — skip the phased build and show progress as nodes from day one? Would need to weigh against the PRD's own reasoning for deferring it (P0 ships on existing surfaces to keep scope small).

What changed, and why

  1. 1No more explicit invocation path — no author toggle, no "+" picker in the composer. The model alone judges whether a request needs to become a goal-based session, every time.Source: Bakery feedback (Nik, Giulio) — resolves former Open question #4
  2. 2A plan is no longer guaranteed. Some goals get one to approve; others are simple enough that the agent just starts working. Either way, approval still happens whenever a plan exists.Source: Bakery feedback — Nik: "the plan keeps changing to fit the goal"; Giulio: "plan and long-running don't go together"
  3. 3A plan isn't fixed once approved — new steps can surface hours or days later as the agent learns more. The agent says this upfront, so it isn't a surprise later.
  4. 4Trace is graph nodes by default now, not a phased future addition — resolves former Open question #5. The kanban variant is dropped.Source: Bakery feedback — Tuukka: kanban isn't a native n8n visualization
  5. 5Each node shows the agent's reasoning for that step, not just which tool it called.Source: Bakery feedback (Sim)
  6. 6Mid-run checkpoints are visible in the trace, and a session can restart from one instead of the very beginning.Source: Bakery feedback (Aniol)
  7. 7Visibility is designed for two states, not one — live while you're watching, and catching up on everything that happened while you were away.

What changed, and why

  1. 1No more explicit invocation path — no author toggle, no "+" picker in the composer. The model alone judges whether a request needs to become a goal-based session, every time.Source: Bakery feedback (Nik, Giulio) — resolves former Open question #4
  2. 2A plan is no longer guaranteed. Some goals get one to approve; others are simple enough that the agent just starts working. Either way, approval still happens whenever a plan exists.Source: Bakery feedback — Nik: "the plan keeps changing to fit the goal"; Giulio: "plan and long-running don't go together"
  3. 3A plan isn't fixed once approved — new steps can surface hours or days later as the agent learns more. The agent says this upfront, so it isn't a surprise later.
  4. 4Trace is graph nodes by default now, not a phased future addition — resolves former Open question #5. The kanban variant is dropped.Source: Bakery feedback — Tuukka: kanban isn't a native n8n visualization
  5. 5Each node shows the agent's reasoning for that step, not just which tool it called.Source: Bakery feedback (Sim)
  6. 6Mid-run checkpoints are visible in the trace, and a session can restart from one instead of the very beginning.Source: Bakery feedback (Aniol)
  7. 7Visibility is designed for two states, not one — live while you're watching, and catching up on everything that happened while you were away.

How this works now

How this works, in a nutshell

1
Judge, maybe plan
The agent alone decides if a request needs to go goal-based, and if it needs a plan at all. Simple, obviously-scoped requests skip both.
→
2
Approve, if there's a plan
Shown before it starts, flagged as something that may change — not a fixed contract. Skipped entirely if no plan was needed.
→
3
Work it, visibly
Graph nodes show progress and reasoning, not just tool calls. Checkpoints let you restart partway through, not just from the beginning.
→
4
Done, plainly
Finishes and tells you what it did — the full trace stays available afterward, whether you watched it happen or not.

Approval mode, in detail

The full picture behind the compact picker in Agent Author's Settings below — MVP decision #6's named presets, each grounded in what it actually changes for the consumer.

Ask before everything

Every tool call needs approval, every time — including the "not risky" ones below. Highest oversight, slowest to run unattended. Good fit while an agent is new and unproven.

Ask only for risky actions — default

Only actions on the "Risky" list below need approval (sending outreach emails, spending money, publishing, etc.). Everything else runs without asking. The balance most agents should ship with.

Don't ask, just notify

Runs fully autonomous, notifies after the fact instead of asking first. Real spend beyond the cost cap and irreversible actions still always ask (Design principle #4) — this mode can't override those hard gates.

Per tool — advanced

Set approval on or off for each tool individually — the same list as "Risky vs. not risky" below, one row at a time. For when a preset doesn't quite fit this agent.

For reference — GitHub Copilot's own session modes
  • Interactive: you and the agent work together — it suggests changes and waits for your input before proceeding.
  • Plan: the agent creates a plan first. You review and approve the plan before it executes.
  • Autopilot: the agent works fully autonomously, without waiting for input.
