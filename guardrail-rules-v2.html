🧩 Problem

The rules that bound an agent don't live in one place, and shouldn't: rate limits belong at project or instance level, inbound restrictions on the channel, timeouts in Settings, memory rules attached to persistence, tool permissions per tool. Scattered by design — but that leaves a builder with no way to answer “what is this agent actually allowed to do?” before putting it in production.

Source: Dimensions to guardrail an agent (Notion), plus Sin's comments on it, Oct 4–6
🧪 Hypothesis

A rule lives wherever the thing it constrains lives: identities in the channel, permissions on the tool, spend in Settings. The exception is content — nothing about what a message contains can be checked with a form field, so those become a guardrail object you build once and attach wherever it should run. Everything else that looked like it needed a new panel turned out to have a home already.

Open questions

Still unanswered after the 22 Oct review

The review settled most of the structure. These are what's left, and the first three block design rather than engineering.

  1. Does the Skills pattern transfer wholesale? Mostly answered rather than open: Skills already ships a reusable object at Settings → Context with a three-rung scope, a usage count, a read-only state and a deletion rule, and a guardrail wants all four. What needs deciding is whether guardrails share that page as a second tab or get their own, and whether a guardrail may be scoped above the person who has to live with it — a Global one set by an admin is, in effect, instance policy by another route.
  2. Is the PII row in Advanced just a guardrail with a shortcut? Both exist on the page and both have the same four hooks. Either the row creates a guardrail behind the scenes, or there are two doors to one room and they'll drift.
  3. Who owns content policy — us or the instance? If an admin sets it, this is read-only for the builder. But a single-user account has no admin, and nobody knows whether instance policies exist outside enterprise. Needs the conversation with Jan's team.
  4. Is never stop really the default when nobody answers an approval request? It contradicts the reasoning used to cap the wait options at a day.
  5. Does “no rule” mean unfinished? An agent with no content check may be perfectly fine. If the summary styles every gap as a warning, builders will either chase them all or stop reading it.
  6. Where does the summary live between publishes? It's shown at publish, but the question it answers comes back later.

Parked on purpose

Agreed to be guardrails, agreed to be out of scope for now.

  1. Sandbox command execution — whitelisting what can run, modes, watching for suspicious activity.
  2. Network egress.
  3. Guardrails on the raw message in and out of the agent — what the current AI Agent node has. Probably workflow hooks; no home picked.
  4. Tool response max size — exists today, not tunable, likely an environment variable rather than UI.

Revised after the 22 Oct review with Michael, Anne and Sin — roughly half of what was here is gone, and the notes say why rather than quietly deleting it.

What the review changed

The short version, so the sections below read in the right light.

  1. Cut: cost cap per operation, max runs per hour, per-tool spend, the content policy card, and the central “who it can message” panel.
  2. New shape: a guardrail is its own reusable object — built once, applied to many tools — not a form inside each tool.
  3. Content checks need a model, not a list. PII detection via a model trained for it; anything else is a workflow hook you write.
  4. Reach is both: identities go to the channel, and one Allow / Block row stays in Settings. A genuinely global rules engine is P1.
  5. The summary view is P1 and moves to publish time.

Telegram's wording doesn't survive the move. “Private” there means a list of usernames; Slack has channels, workspaces and groups, so the same two options would be a lie. The shape transfers, the labels don't — and whoever builds this will have to answer it per channel, which is an argument for doing one channel properly rather than all five shallowly.

We looked at doing this centrally instead, and dropped it. The deciding argument was the builder's: you set this while you're in the channel's head, not while reading a list. Michael: “then I would probably get rid of the central aspect.”

What that leaves without a home. One rule genuinely isn't channel-specific: whether anyone other than the person who started the run can talk to the agent. That one isn't ours — it's access, Michael is building it, and it's listed under What isn't a guardrail below. Everything on this screen stays with the channel that owns the identities.

2 — Tools  permissions here, checks in a guardrail you reuse

Permissions already exist and are better than what I'd invented: set per group — read-only versus write and delete — with per-tool override, inside the tool's own setup. What's new is everything else. The checks and limits don't live in the tool at all: a guardrail is its own object, built once and applied to as many tools as you like.

Why not a row inside Capabilities, which was the other option. That card says “what this agent can do and how it does it”, and a guardrail is the opposite — what it must not do. Filing a restriction there makes the card's own description untrue, and buries the thing an auditor scans for under three rows about what's enabled. Skills already proves a sibling card is the pattern for this, so it costs nothing to follow.

The order carries the argument. Capabilities, then Guardrails, then Memory reads as what it can do → what bounds it → what it keeps — the order a run moves in, and the order someone reviewing an agent asks about.

One thing a roster has that the tool pane doesn't. Each row says where it's attached — Notion · input, 4 tools · output. From inside a tool you only ever see that tool's two slots, so a guardrail applied to nine tools looks identical to one applied to one. The roster is the only place the blast radius is visible, which is also what makes editing safe to offer from here.

Tools and Skills are different things. A skill is a markdown instruction package — “how this agent handles specific tasks”. Guardrails attach to tools, not skills. Worth keeping straight, because the doc uses “Skills” for the allowed-tools list.

Creating one new

Half of this exists already: the Guardrails node ships the detectors and the check-or-sanitize decision, and this modal reuses both. What's new is attaching one to a tool rather than dropping a node into a workflow. Guardrails are for tools only right now, so it reads in the order the decision is made: where in the tool call it runs, then how it checks, then the limits. Everything that used to be drawn inside the tool pane — data checks, timeouts, rate limits — moved in here, because configuring that per tool means filling the same form nine times and storing nine copies of it. The name is the modal's title, edited in place, so the form opens on the decision rather than on a label.

Scoping is out for now, and that has a consequence worth saying. Without where can this be used, a guardrail belongs to the agent you made it in — so the reuse argument only holds within one agent, which is still the case that hurts most (nine data-table tools, one form). Reuse across agents, and the Global / project / agent ladder that Skills already ships, becomes P1. The library screen below is drawn with that ladder, so it's ahead of this modal until the two are reconciled.

Tags, not pickers, and more than one per slot. A tool can need two checks on the way in — redact PII, and refuse anything with finance data in it — which a single dropdown can't express. Tags also say the right thing about ownership: they're read-only here because the guardrail belongs to the library, not to this tool. You attach and detach from the pane; you edit from the guardrail.

And when the limit is reached is its own row, not part of a guardrail. It belongs to the tool rather than to any check attached to it: a rate limit is a property of the API behind the tool, and the answer — wait and retry, skip, stop — is the same whichever guardrails happen to be attached. Folding it into one of them would mean the behaviour changed depending on which guardrail you detached.

Two entry points because they're different moments. Add guardrail picks one that exists; Create guardrail opens the modal. Separating them means the common case — reusing the one you already made — isn't behind a menu that also offers to make a new one.

A guardrail is one check at one point. Where it runs is a single choice: checking what you send to a tool and checking what comes back are different decisions about different payloads, and bundling them into one object makes it vague what you actually switched on. To cover both you attach two, which also reads better in the library — “Finance check, on Notion, after a tool call” is a concrete thing, where “Finance check, on four hooks” is a configuration you'd have to open to understand.

Why wait and retry can ship as the default. It's the only one of the three that can't lose you anything: hitting a rate limit and backing off changes how long a run takes and nothing else, where skipping the call silently drops work and stopping the run throws away everything done so far. A default is safe to set when the worst case is slowness.

Two options rather than a toggle, because they aren't the same kind of answer. A toggle makes all tools look like the on state of a setting whose off state is nothing; in fact both options are real choices and the second one needs a list. Showing the field only when Select tools is active also stops the common misread: a populated tag field sitting under an enabled All tools toggle looks like it's narrowing the scope when it isn't doing anything.

All tools stays the default. A guardrail you went to the trouble of creating is usually meant to apply, so making you list the tools is work that produces the answer you already had. The deciding case is the one a list gets wrong silently: a tool added next month is covered by all and missed by an enumeration nobody remembers to update.

Two entry points, and they want opposite flows. From a tool you attach one guardrail to one tool, which is the natural move while you're setting that tool up. But the moment you have nine data-table tools, you want the other direction: make the guardrail, then tick the tools it covers — which is why Applies to is in the modal rather than only on the tool. Both exist above. The list itself isn't a new invention — it goes beside Skills in Settings → Context, drawn in the next section.

What a separate object costs. It stops being a setting and becomes a thing with a lifecycle: it can be shared, orphaned, edited from under a tool that depends on it, and deleted. Michael: “when do they stop existing? If they're not in use, does that remove them, or is there somewhere you can actually delete them?” Most of that is already answered — by Skills, which has the same lifecycle and solved it. The next section is that answer. The part it doesn't cover is editing: changing one silently changes every tool using it.

And it answers Michael's lifecycle question without us designing anything. Skills can't be deleted while they're attached: “Used by 3 agents. Remove the skill from each agent first.” No cascade, no orphans, no silently breaking an agent you can't see. Inherited ones say “You can use but not change this skill”, which is the same read-only state we drew for the PII row in section 3 — arrived at twice, independently, which is a good sign it's right. Moving one between scopes even has its own rule: you need delete permission, because moving removes it from where it is.

Where a guardrail is not like a skill, and it matters. A skill is additive: worst case the agent ignores it and behaves as it would have anyway. A guardrail is subtractive — if it stops applying, something gets out. So the same table carries more risk: editing a Global guardrail changes 12 agents at once, and the delete rule protects the object without protecting the agents from an edit. Skills doesn't need an impact warning before saving. Guardrails probably do, and that's the one screen this pattern doesn't hand us.

Not styled as a warning, on purpose. Editing a shared guardrail is a normal thing to do — it's the reason the object exists. The dialog's job is to make the blast radius visible, not to imply a mistake, which is the same reasoning behind the summary view using grey for an unset rule rather than red. 3 — Cost  nothing to add

I had two new rows here and both are gone. This is the section where the review cut the most, so what's drawn below is the card exactly as it ships today — included so the cuts are legible, not because anything changes.

The card is unchanged, so it's only drawn once — in the assembled Settings view at the end.

Cost cap per operation is out. You can't know what a call costs until it has cost it. Pricing it in advance would mean running the model's own tokenizer over the input first, which is itself a cost, and the output price isn't knowable at all. Michael: “the only way we can know cost about the model is to send it to the model and then it tells us what it costs.” What replaces it isn't in this card: a timeout and a calls-per-minute limit, both in the guardrail object in section 2. Those bound the two things we can actually measure before the fact.

Max runs per hour is out too. Not because it's hard to build — because nobody can set it. A run isn't a unit a builder has a feel for: one message, one session, a sub-agent's work? Two people with long sessions look identical to one runaway loop. The budget already bounds the thing anyone actually cares about, in a unit they understand. Michael: “I would just remove it. The cost cap is the best measurement.”

Which leaves this section with no new control at all — and that's the useful result. Every cost guardrail worth having either already exists here, or turned out to belong to a tool rather than the agent. The one open thread is per-tool override: we're starting with one global setting, and only splitting it per tool if people ask. Michael: “per tool is going to add a lot of configuration that's not going to be used an awful lot.”

The types aren't ours to invent — the Guardrails node already ships them. Keywords, Jailbreak, NSFW, Personal Data (PII), Secret Keys, Topical Alignment, URLs, Custom, Custom Regex, each with its own options: PII takes All or Selected entities, Secret Keys takes a permissiveness, the detection ones take a confidence threshold. Reusing that list means a builder who has used the node recognises every option, and we inherit detectors that already exist rather than describing ones that don't.

The node also answers what happens when it catches something, and it's two things, not one. Its Operation is Check Text for Violations or Sanitize Text — validate and fail, or redact and carry on. That's a real choice a builder makes per guardrail, so it gets its own section: Block the call / Redact and continue / Ask first. I had it as a vague If it fires at the bottom of the form; this is the same question asked in the product's own terms.

And timeout and rate limit came back out. I'd folded them into What it does last round. The node's taxonomy settles it: every guardrail in it is a content check, and a timeout isn't content. They belong to the tool, which is where When the limit is reached already sits.

Labels: short noun phrases, not questions. What it does · If it finds something · When it runs · Which tools · Which operations. Parallel grammar so the modal reads as one sentence being filled in, and short enough that five sections don't feel like a survey.

Which operations only works for MCP, and the field has to admit it. An MCP server declares whether each tool reads or writes; a workflow tool or a node tool doesn't. So narrowing a guardrail to write-and-delete silently covers nothing on the tools we can't classify. That's in the tooltip now, and it's the same limit Michael raised about the summary — “there's no way to know for sure all write tools have approval, as we don't know what a write tool is for workflows or node tools.”

One dropdown on the row, and the modal disappears. It only ever held a single field, which is not worth a screen. More to the point, this is already how the card works: Memory model and Cache duration are both pickers sitting on their own row, so the new control is the same shape as its neighbours instead of the one thing in Advanced that opens something.

And the switch goes with it. A separate on/off plus a model picker is two controls answering one question, with a nonsense state available — on, with no model. The picker carries both: Off is a value in the list. Reading the row left to right now gives you the whole answer without opening anything.

No hooks to pick, and that's the difference from a guardrail. A guardrail is one check you attach at one point, so it asks where. This is a standing policy — switching it on means everywhere the agent could leak something, so asking where would only offer people a way to leave a hole in it. The row states the coverage instead of making you assemble it, which also makes the two impossible to confuse: one has a where, the other doesn't.

What isn't a guardrail  cut from this project

Two things I had drawn as guardrails aren't, and Michael is building them. Keeping them on this page would have us designing the same screens twice and disagreeing with ourselves in review.

Michael owns these

  1. Who can talk to the agent. Whether anyone other than the person who started a run can reach it. A permission, not a check on what passes through.
  2. Where it asks for approval. Routing a human-in-the-loop request when a scheduled run has nobody waiting, and what happens if nobody answers. That's the approval mechanism, which guardrails use but don't define.

The line that separates them is worth keeping. A guardrail inspects something passing through the agent and can stop it. Access decides who may start a conversation; approval routing decides who gets interrupted when something pauses. All three feel like safety and only one is a guardrail — which is exactly why they kept drifting onto this page.

Seen whole, the additions are smaller than the tab already is. Sub-agents alone carries five controls and three model pickers; Advanced carries five more. Two new cards of one and two rows, plus one row in Advanced, is not what tipped this tab into being a lot — it was a lot already. That's an argument for the additions and also a warning: the next one genuinely won't fit, and the honest response then is to group rather than stack.

What the summary view costs now. With rules this distributed, a builder has even less chance of seeing the whole picture: channel modals, a guardrail object, two Settings cards. That's the argument for Agent summary — except it's now P1 and moves to publish time, so for the whole of P0 there is no single place to read what an agent is allowed to do. Worth naming as a known gap rather than pretending the distribution is free.

The question the whole page used to hang on is now answered. Sin's doubt on the doc was whether form fields could express any of this: “Could this even be possible — do we want this to be available?” The review answered it both ways. Permissions, limits and routing stay as form fields, because they bound things we can actually measure. Anything about content doesn't — it's a model or a workflow you attach. That split is why the guardrail object exists, and it's the single biggest change on this page.
