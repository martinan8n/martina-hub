Guardrails v4

Only the screens that survived. The wider dimensions work — reach, cost, memory, the summary — either moved to its own workstream or turned out not to be a guardrail; the history is in v2. What's left is one object: a check you build once and attach to a tool. Hi-fi lives in Guardrails hi-fi.

🧩 Problem

An agent calls tools, and nothing inspects what passes through them. Permissions decide whether a tool runs; nothing looks at what it was sent or what came back. The checks that could do it already exist as a workflow node — they just can't be attached to an agent.

Source: Dimensions to guardrail an agent (Notion), the 22 Oct review, and the Guardrails node
🧪 Hypothesis

A guardrail is its own object: one check, attached at one point, reusable across tools. Its types are the node's — PII, Jailbreak, NSFW, Secret Keys, Topical Alignment, Keywords, URLs, Custom — plus a workflow, plus the two limits. Nothing about it is invented; the new part is attaching it to an agent rather than dropping a node in a flow.

Agent level is P0. Instance exists already; project level is open.

Open questions

Still open

From the board, and from building it.

  1. Which level does a guardrail belong to? Agent is P0. Instance already exists — Settings → Policies ships today with data redaction and access policies. Project level is the open one, and it's what the centralised ask needs: “as a user, I have a centralised place where I can set up the guardrails for all my automations.”
  2. Guardrails are not Context. I'd drawn the library as a second tab beside Skills under Settings → Context, on the grounds that Skills solves the same reuse problem. That's a mechanism match, not a meaning match — Context is what the agent knows, a guardrail is what it may not do. The instance equivalent is Policies, so the library probably belongs there instead.
  3. Which guardrails go to instance settings? Needs Jan. The Policies page already has the shape, including a per-node Access policies modal that restricts individual actions — worth checking whether a guardrail is a new kind of policy or an extension of that one.
  4. Approvals don't exist yet. So the admin-approval state — ask an admin to allow this — can't be built, and nor can anything that pauses for a person. Everything here has to work without it.
  5. What does an agent look like before any of this is configured? Drawn as an empty card with one Add guardrail. Worth a state for the moment a builder has never seen the concept.
  6. Can a suggestion be dismissed? The Build card suggests two and there's no way to say no.

Where this has got to

The shape after the 22 Oct review and the rounds since, so the sections below read in the right light.

  1. A guardrail is its own object — built once, attached to many tools. Its types aren't ours: the Guardrails node already ships them, and the modal reuses that list plus a workflow and the two limits.
  2. It attaches per slot. A tool has Input and Output, each holding any number of guardrails as tags, with one Add guardrail per slot.
  3. Limits are guardrails too, grouped apart because they aren't about content. They bring When the limit is hit with them, which is why the tool pane shows that row only when one is attached.
  4. Cut: cost cap per operation, max runs per hour, per-tool spend, the content policy card, and the central “who it can message” panel.
  5. Not ours: access and approval routing are Michael's. The summary view moved to Agent summary.

Build today today

Permissions already exist and are better than what I'd invented: set per group — read-only versus write and delete — with per-tool override, inside the tool's own setup. What's new is everything else. The checks and limits don't live in the tool at all: a guardrail is its own object, built once and applied to as many tools as you like.

Memory

What this agent remembers

Two guardrails are already there before anyone does anything. PII redaction and Secret keys are Global — set once at instance level and inherited by every agent. They show with a globe and no ×, because a builder can see what they inherit but can't drop it. Drawing them as ordinary chips with the locally-added one beside them is deliberate: what matters to the person reading the card is what's protecting this agent, not who decided it. The globe answers who, quietly, for anyone who asks.

The suggestions are the part that might actually get used. An empty Guardrails card asks a builder to know what could go wrong, which is a lot to ask of someone whose agent works fine in testing. Suggesting from what the agent already has — it posts to Slack, so check what it sends; it reads Notion, so check what comes back — turns the blank card into two decisions with an obvious answer. One click adds; the chip becomes a normal one.

They say why they're suggested, and that's the part to get right. Suggested, because this agent writes to Slack and reads Notion is checkable — a builder can agree or disagree with the premise. Without it they're a product opinion with no argument, which is how suggestions get ignored. It also keeps us honest: if we can't write the reason in one line, the suggestion probably isn't good enough to make.

Why not a row inside Capabilities, which was the other option. That card says “what this agent can do and how it does it”, and a guardrail is the opposite — what it must not do. Filing a restriction there makes the card's own description untrue, and buries the thing an auditor scans for under three rows about what's enabled. Skills already proves a sibling card is the pattern for this, so it costs nothing to follow.

The order carries the argument. Capabilities, then Guardrails, then Memory reads as what it can do → what bounds it → what it keeps — the order a run moves in, and the order someone reviewing an agent asks about.

One thing a roster has that the tool pane doesn't. Each row says where it's attached — Notion · input, 4 tools · output. From inside a tool you only ever see that tool's two slots, so a guardrail applied to nine tools looks identical to one applied to one. The roster is the only place the blast radius is visible, which is also what makes editing safe to offer from here.

Tools and Skills are different things. A skill is a markdown instruction package — “how this agent handles specific tasks”. Guardrails attach to tools, not skills. Worth keeping straight, because the doc uses “Skills” for the allowed-tools list.

The slots are Input and Output, and the sub-line carries the moment. I'd renamed them to Before the call / After the call to match the guardrail's own When it runs, on the theory that two vocabularies make a builder translate. That theory was weak — the picker only offers guardrails that fit the slot, so the product does the translating, not the person.

And the rename broke on the second example. With a rate limit attached, Before the call — checks what the agent is about to send was simply false: a limit doesn't look at the payload at all. Once limits became guardrails, the slot stopped meaning “what gets inspected” and started meaning “what runs at this point”. So the label names the side — Input, Output — and the line underneath names the moment without promising an inspection: runs before the call is made.

One action per slot, not one for the pane. I had Add guardrail and Create guardrail at the bottom, which is wrong twice over: two links for what is really one job, and neither says whether it would attach to Input or Output. Moving a single + Add guardrail into each row fixes both — the slot is implied by where you clicked, and creating is just the last item in the picker, where it belongs as the fallback for “none of these”.

Editing lives on the tag. The tag is the guardrail, so clicking its name opens it and the × detaches it. That also keeps the two actions honestly different: detaching affects this tool, editing affects every tool using it, which is why a save from there goes through the impact notice drawn further down.

The empty state is the same pane with the tags missing. No illustration, no explanatory panel that disappears once you use it — the rows stay put so the pane doesn't reflow the moment you add the first one, and the only thing you can do is the thing you came for.

Making one new

A content check

Half of this exists already: the Guardrails node ships the detectors and the check-or-sanitize decision, and this modal reuses both. What's new is attaching one to a tool rather than dropping a node into a workflow. Guardrails are for tools only right now, so it reads in the order the decision is made: where in the tool call it runs, then how it checks, then the limits. Everything that used to be drawn inside the tool pane — data checks, timeouts, rate limits — moved in here, because configuring that per tool means filling the same form nine times and storing nine copies of it. The name is the modal's title, edited in place, so the form opens on the decision rather than on a label.

One pane, three guardrails, and the limit row is a consequence. I'd drawn a second pane for the limit example — the whole thing again, header and permissions and both slots, to show one extra row. That's the duplication we cut from Settings, and it also made the two look like different screens. This tool has a content check, a PII redaction and a rate limit attached at once, which is the ordinary case, and When the limit is hit appears because one of the tags is a limit. Detach Slow API back-off and the row goes with it.

And the PII modal loses the failure section. I'd added If the check doesn't answer for the case where the model is down — fail closed or fail open. It's a real decision and it wasn't the node's, it was mine, and it made a content check look like it had a limit. Out, for the same reason Ask first went. It should come back as an engineering question about what the runtime does when a check errors, not as a control invented on a mockup.

Everything that depends on the type is now inside a rule, everything that doesn't sits outside it. Picking Personal Data (PII) changes three things — which entities, what happens on a catch, what happens when the check fails — and they were drawn at the same level as Which tools, which doesn't change at all. The indent says which sections would be replaced if you switched the type to Rate limit, and which would stay exactly as you left them.

Same question, two controls, and the rule is the container. When the limit is hit is a segmented row inside the create modal and a dropdown in the tool pane. That isn't an inconsistency: in the modal it's a full-width section where you're deciding, and seeing all three options at once is the point. In the pane it's a right-aligned control in a row where you're reviewing, next to permissions and credentials that are all dropdowns — a segmented control there would be the only one of its kind and would crowd the row. Segment where there's room and a decision, dropdown where there's a row and a glance.

Where these three came from, since two are the product's and one is mine. Block the call and Redact and continue are the Guardrails node's two operations — Check Text for Violations, which has Pass and Fail outputs, and Sanitize Text, “redact text to mask personal data, secret keys, URLs”. All I did was say what they mean once the guardrail is attached to a tool instead of sitting in a workflow.

There was a third option and I'd made it up. Ask first came from the agent's permission vocabulary, where require_approval reads that way. The node has no approval concept, so putting it here promised a human pause whose plumbing isn't ours — who gets asked, where it goes when a scheduled run has nobody waiting, what happens if nobody answers. All of that is under What isn't a guardrail and belongs to Michael. Removed rather than dimmed: an invented option on a mockup gets quoted back as a decision.

The form is the same every time; only the indented block changes. Four sections are always there — What it does, When it runs, Which tools, Which operations — and everything that depends on the type sits indented under the first. A PII guardrail gets entities and If it finds something; a rate limit gets calls per minute and When the limit is hit. Switching the type swaps that block and leaves the rest of your answers alone, which is the point of drawing the two side by side.

I'd written that When it runs and Which operations drop out for a limit. They don't. Rate-limiting only the write operations of a tool is a reasonable thing to want, and a limit still has to be checked at a moment — before the call, in practice. Dropping them would have made the form change shape by type, which is exactly what makes a form feel unpredictable.

I took these out last round and that was wrong. My argument was that the node's taxonomy is all content, so a timeout isn't a guardrail. But the node is a workflow step you drop into a flow; what we're building is a thing you attach to a tool, and from the tool's point of view a rate limit and a PII check are the same kind of attachment — something that can interrupt the call. Grouping them under Not about content in the picker keeps the distinction visible without splitting the object in two.

Which means the tool pane loses a row. When the limit is reached was sitting there as a property of the tool. With limits as guardrails it would be the same decision in two places, so it goes — a tool with a rate limit now has a rate-limit guardrail attached, and the answer lives in it.

The types aren't ours to invent — the Guardrails node already ships them. Keywords, Jailbreak, NSFW, Personal Data (PII), Secret Keys, Topical Alignment, URLs, Custom, Custom Regex, each with its own options: PII takes All or Selected entities, Secret Keys takes a permissiveness, the detection ones take a confidence threshold. Reusing that list means a builder who has used the node recognises every option, and we inherit detectors that already exist rather than describing ones that don't.

The node also answers what happens when it catches something, and it's two things, not one. Its Operation is Check Text for Violations or Sanitize Text — validate and fail, or redact and carry on. That's a real choice a builder makes per guardrail, so it gets its own section: Block the call / Redact and continue. I had it as a vague If it fires at the bottom of the form; this is the same question asked in the product's own terms, and only in those terms.

And timeout and rate limit came back out. I'd folded them into What it does last round. The node's taxonomy settles it: every guardrail in it is a content check, and a timeout isn't content. They belong to the tool, which is where When the limit is reached already sits.

Labels: short noun phrases, not questions. What it does · If it finds something · When it runs · Which tools · Which operations. Parallel grammar so the modal reads as one sentence being filled in, and short enough that five sections don't feel like a survey.

Which operations only works for MCP, and the field has to admit it. An MCP server declares whether each tool reads or writes; a workflow tool or a node tool doesn't. So narrowing a guardrail to write-and-delete silently covers nothing on the tools we can't classify. That's in the tooltip now, and it's the same limit Michael raised about the summary — “there's no way to know for sure all write tools have approval, as we don't know what a write tool is for workflows or node tools.”

One dropdown on the row, and the modal disappears. It only ever held a single field, which is not worth a screen. More to the point, this is already how the card works: Memory model and Cache duration are both pickers sitting on their own row, so the new control is the same shape as its neighbours instead of the one thing in Advanced that opens something.

And the switch goes with it. A separate on/off plus a model picker is two controls answering one question, with a nonsense state available — on, with no model. The picker carries both: Off is a value in the list. Reading the row left to right now gives you the whole answer without opening anything.

No hooks to pick, and that's the difference from a guardrail. A guardrail is one check you attach at one point, so it asks where. This is a standing policy — switching it on means everywhere the agent could leak something, so asking where would only offer people a way to leave a hole in it. The row states the coverage instead of making you assemble it, which also makes the two impossible to confuse: one has a where, the other doesn't.

Scoping is out for now, and that has a consequence worth saying. Without where can this be used, a guardrail belongs to the agent you made it in — so the reuse argument only holds within one agent, which is still the case that hurts most (nine data-table tools, one form). Reuse across agents, and the Global / project / agent ladder that Skills already ships, becomes P1. The library screen below is drawn with that ladder, so it's ahead of this modal until the two are reconciled.

Tags, not pickers, and more than one per slot. A tool can need two checks on the way in — redact PII, and refuse anything with finance data in it — which a single dropdown can't express. Tags also say the right thing about ownership: they're read-only here because the guardrail belongs to the library, not to this tool. You attach and detach from the pane; you edit from the guardrail.

Two entry points because they're different moments. Add guardrail picks one that exists; Create guardrail opens the modal. Separating them means the common case — reusing the one you already made — isn't behind a menu that also offers to make a new one.

A guardrail is one check at one point. Where it runs is a single choice: checking what you send to a tool and checking what comes back are different decisions about different payloads, and bundling them into one object makes it vague what you actually switched on. To cover both you attach two, which also reads better in the library — “Finance check, on Notion, after a tool call” is a concrete thing, where “Finance check, on four hooks” is a configuration you'd have to open to understand.

Why wait and retry can ship as the default. It's the only one of the three that can't lose you anything: hitting a rate limit and backing off changes how long a run takes and nothing else, where skipping the call silently drops work and stopping the run throws away everything done so far. A default is safe to set when the worst case is slowness.

Two options rather than a toggle, because they aren't the same kind of answer. A toggle makes all tools look like the on state of a setting whose off state is nothing; in fact both options are real choices and the second one needs a list. Showing the field only when Select tools is active also stops the common misread: a populated tag field sitting under an enabled All tools toggle looks like it's narrowing the scope when it isn't doing anything.

All tools stays the default. A guardrail you went to the trouble of creating is usually meant to apply, so making you list the tools is work that produces the answer you already had. The deciding case is the one a list gets wrong silently: a tool added next month is covered by all and missed by an enumeration nobody remembers to update.

Two entry points, and they want opposite flows. From a tool you attach one guardrail to one tool, which is the natural move while you're setting that tool up. But the moment you have nine data-table tools, you want the other direction: make the guardrail, then tick the tools it covers — which is why Applies to is in the modal rather than only on the tool. Both exist above. The list itself isn't a new invention — it goes beside Skills in Settings → Context, drawn in the next section.

What a separate object costs. It stops being a setting and becomes a thing with a lifecycle: it can be shared, orphaned, edited from under a tool that depends on it, and deleted. Michael: “when do they stop existing? If they're not in use, does that remove them, or is there somewhere you can actually delete them?” Most of that is already answered — by Skills, which has the same lifecycle and solved it. The next section is that answer. The part it doesn't cover is editing: changing one silently changes every tool using it.
