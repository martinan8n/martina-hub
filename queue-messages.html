01 / Problem

While an agent works, I notice something to add or correct. I need to know whether my message was saved, when it will be read, and whether I can still change it. Three pending messages must feel as understandable as one.

“Send now” is ambiguous if it secretly cancels a tool. Sending an update must preserve the running job.

Evidence & starting point

Dylan asked for multiple-message behavior and access to the full message. Craig proposed delivery after the next tool completes, batching pending messages, and a five-message limit. His cancellation behavior is superseded by the direction below.

02 / Proposal

Sending a message never stops the job.

Default to Update current task. Save the message immediately and apply it at the next safe point, after the current action finishes. If that action is slow, say what we are waiting for.

Update current task

“Only include enterprise accounts.”

Steers the work already in progress. Pending updates are delivered together, in order, at the next safe point. The task continues with the new context.

After this task

“Then make a summary for the team.”

A separate follow-up. It waits for the current task to finish, then starts as a new turn. Several follow-ups run one at a time, in their displayed order.

Pause / stop

“Pause task” or “Stop task”.

Separate, explicit task controls. Pause keeps a resumable task; Stop ends it. Neither is attached to Send. Explicit stop requests in chat must also be honored.

Copy decision: replace “Send now” with “Update current task”. “Now” should describe saving the update, not promise immediate interruption.

04 / UX logic

Saved → pending → applied → continue

MomentWhat the user seesBehavior
Send while runningA gray message row, full-text disclosure, and “After current action”.Persist first, acknowledge second. Keep the current tool and job running. Failed saves retain the draft and offer Retry.
Multiple updatesCount + separate rows in submission order. A bounded scroll region after several entries.Batch eligible steering updates at one safe boundary; preserve their identities and order. Never silently merge the visible messages.
Edit / removeEdit that message in place; Save or Cancel. Removing offers Undo.Later entries stay untouched. Hold the edited message and subsequent steering updates until Save/Cancel, to preserve order. Tell the user about this hold.
Next safe pointPending rows move into history, marked Applied; “Adjusting course…”.Atomically claim the batch. Mark Applied only after acknowledgment from the agent. A correction affects future work; it cannot undo a completed external action.
After this taskA row labeled “After task finishes”, ordered with other follow-ups.Start only after successful completion, one follow-up per turn. No automatic start while paused, failed, stopped, or awaiting approval.
Approval / cost capThe existing approval gate replaces the composer. Pending messages remain readable.No message bypasses the gate. Keep the queue intact; continue only after the required decision. Re-evaluate the intended action with fresh instructions afterward.
Pause / stopPause: resumable state. Stop: explicit confirmation that pending messages will not run.Retain pending messages for inspection. Resume is explicit. Never restart a stopped task because a message was pending.
Completion race“Task finished before this update was applied” + explicit Start follow-up.Do not lose a pending steering update or silently claim it was applied. Ask the user to start a follow-up with the remaining context.
Offline / delivery failure“Not delivered” + Retry; full message remains available.Durable storage, unique message IDs and acknowledgment prevent loss and duplicate delivery. Restore the same state after reconnect.

Draft limit: five pending messages, following Craig’s proposal. At the limit, retain the composer draft and explain the limit; editing and removing remain available. This is a product constraint to validate, not a settled technical requirement.

05 / Reuse from goal-based tasks

Keep the familiar task shell.

Reuse

Task header, Running / Awaiting / Paused vocabulary, separate card above the composer, upward expansion, trace entry point, approval gate, and “Adjusting course…” transition.

Add

Pending-message tray, count, full-text expansion, individual editing and removal, timing labels, acknowledgment, and retry. The tray tracks messages; the card tracks the task.

Keep distinct

Stopping a foreground response, pausing a background task, and ending a task are different actions. No generic stop icon beside Send should carry all three meanings.

The source reference docks the task card only when its inline version scrolls out of view. This prototype starts in that docked state. Expand upward over history without shifting the composer; never show two copies of the same task card.

06 / Review scenarios

What this proposal must pass

  • Send three updates during a slow tool call: all remain readable, the action continues, and the next boundary applies the batch in order.
  • Expand a long message, edit the middle entry, cancel the edit, and remove/undo another without changing its neighbors.
  • Queue two follow-ups: neither starts before the current task finishes; each gets its own turn.
  • Hit five messages: keep the unsent draft, allow edits/removals, and explain why Send is unavailable.
  • Pause, encounter an approval gate, fail delivery, or finish before uptake: retain every message and show the correct next action.
  • Use a narrow viewport or keyboard: no horizontal page scrolling; full text and actions remain accessible. Enter sends, Shift+Enter inserts a new line; Escape cancels an inline edit.
07 / Decisions still needed

Agree the contract before shipping.

  1. Safe boundary: engineering must define the next safe point for sequential and parallel tools. The UI must not promise immediate delivery.
  2. Scope: ship steering first, or include “After this task” at launch? The prototype exposes both so the distinction can be reviewed.
  3. Five-message cap: confirm the need and whether editing should temporarily hold the ordered batch.
  4. Stop semantics: agree how explicit stop requests reach a long-running tool. They must use the task-control path rather than wait in the ordinary message queue.
  5. Shared component: align Agents and AI Assistant on timing, acknowledgment, and state labels before reusing the tray across surfaces.

Already aligned: Send does not cancel the current tool or stop the job. Pending text can always be inspected in full. The rest is a draft for review.
