Guardrails — rules & dimensions

Designing the five dimensions from the Dimensions to guardrail an agent doc: where a builder attaches a rule, and how they see what they've actually bounded. Hand-drawn on purpose — none of this is settled. The finished guardrail patterns (cost cap, running states, the trace) live in the Guardrails workstream instead.

🧩 Problem

The rules that bound an agent don't live in one place, and shouldn't: rate limits belong at project or instance level, inbound restrictions on the channel, timeouts in Settings, memory rules attached to persistence, tool permissions per tool. Scattered by design — but that leaves a builder with no way to answer “what is this agent actually allowed to do?” before putting it in production.

Source: Dimensions to guardrail an agent (Notion), plus Sin's comments on it, Oct 4–6
🧪 Hypothesis

A rule lives wherever the thing it constrains lives: identities in the channel, permissions on the tool, spend in Settings. The exception is content — nothing about what a message contains can be checked with a form field, so those become a guardrail object you build once and attach wherever it should run. Everything else that looked like it needed a new panel turned out to have a home already.

Open questions

Still unanswered after the 22 Oct review

The review settled most of the structure. These are what's left, and the first three block design rather than engineering.

  1. Does the Skills pattern transfer wholesale? Mostly answered rather than open: Skills already ships a reusable object at Settings → Context with a three-rung scope, a usage count, a read-only state and a deletion rule, and a guardrail wants all four. What needs deciding is whether guardrails share that page as a second tab or get their own, and whether a guardrail may be scoped above the person who has to live with it — a Global one set by an admin is, in effect, instance policy by another route.
  2. Is the PII row in Advanced just a guardrail with a shortcut? Both exist on the page and both have the same four hooks. Either the row creates a guardrail behind the scenes, or there are two doors to one room and they'll drift.
  3. Who owns content policy — us or the instance? If an admin sets it, this is read-only for the builder. But a single-user account has no admin, and nobody knows whether instance policies exist outside enterprise. Needs the conversation with Jan's team.
  4. Is never stop really the default when nobody answers an approval request? It contradicts the reasoning used to cap the wait options at a day.
  5. Does “no rule” mean unfinished? An agent with no content check may be perfectly fine. If the summary styles every gap as a warning, builders will either chase them all or stop reading it.
  6. Where does the summary live between publishes? It's shown at publish, but the question it answers comes back later.

Parked on purpose

Agreed to be guardrails, agreed to be out of scope for now.

  1. Sandbox command execution — whitelisting what can run, modes, watching for suspicious activity.
  2. Network egress.
  3. Guardrails on the raw message in and out of the agent — what the current AI Agent node has. Probably workflow hooks; no home picked.
  4. Tool response max size — exists today, not tunable, likely an environment variable rather than UI.

What's bounded

One place to read what this agent is allowed to do, with the rules themselves still living where they belong. Two takes on the same content: by dimension, and by the path a run takes. Same agent in both — a weekly metrics sync that posts to Slack.

Revised 22 Oct: this is P1, and it isn't in Settings. It gets built after the permissions it summarises, and it appears when you hit publish — the moment you're actually deciding whether this agent is safe to let out. There's a publish modal in the product already; it says nothing useful. Michael: “I think it would be cool to have a place where you can see all the permissions, but I don't think it's a P0.”

Trade-off between the two. A is easier to extend — a new dimension is a new row, and it survives the rules living in five different places. B teaches the model better and makes the end-of-line gap land, but it implies an order that isn't quite true: cost applies at every stage, not between acting and remembering. B is also harder to grow, since a sixth stage means re-cutting the row.

Publish answers when, not where. Showing this before you publish catches the one moment a builder is receptive to it. But it's a modal you dismiss, and the question comes back a week later when you're wondering why the agent didn't post something. So it needs a second, permanent entry point — an icon on the agent, a line in the trace, somewhere in Build — and that's undesigned. Putting it in Build was the first instinct and it clutters a page that's already full.

Both takes assume the rules exist. Every pill above reads a state we haven't built yet. If this ships before the permissions it summarises, it summarises nothing — which is exactly the argument for it being P1, and the reason it's drawn here rather than queued.

Where rules get configured

One section per dimension, each control drawn inside the real container it would ship in. Marked today if it exists in the product now, or new if it doesn't. Revised after the 22 Oct review with Michael, Anne and Sin — roughly half of what was here is gone, and the notes say why rather than quietly deleting it.

What the review changed

The short version, so the sections below read in the right light.

  1. Cut: cost cap per operation, max runs per hour, per-tool spend, the content policy card, and the central “who it can message” panel.
  2. New shape: a guardrail is its own reusable object — built once, applied to many tools — not a form inside each tool.
  3. Content checks need a model, not a list. PII detection via a model trained for it; anything else is a workflow hook you write.
  4. Reach is both: identities go to the channel, and one Allow / Block row stays in Settings. A genuinely global rules engine is P1.
  5. The summary view is P1 and moves to publish time.

Telegram already ships this, as step 2 of a vertical stepper: Add credential → Set access and restrictions → Connect Telegram. Every other channel takes a different path — a credential block and then the channel's own fields, with no access step at all. So the work isn't designing a control, it's giving the other channels the step Telegram has.

Telegram's wording doesn't survive the move. “Private” there means a list of usernames; Slack has channels, workspaces and groups, so the same two options would be a lie. The shape transfers, the labels don't — and whoever builds this will have to answer it per channel, which is an argument for doing one channel properly rather than all five shallowly.

We looked at doing this centrally instead, and dropped it. A single card in Settings listing who the agent can talk to reads well until you try to fill it: every identity in it belongs to one channel, so the control has to reach into Slack, Telegram and the rest to populate itself, and you'd still be configuring Slack — just somewhere further from Slack. The deciding argument was the builder's: you set this while you're in the channel's head, not while reading a list. Michael: “then I would probably get rid of the central aspect.”

What that leaves without a home. One rule genuinely isn't channel-specific: whether anyone other than the person who started the run can talk to the agent. That's true wherever it's used, so it can't live in a channel — it goes in Settings as a single Allow / Block row, drawn in section 5. Everything else here stays with the channel that owns the identities.

2 — Tools  permissions here, checks in a guardrail you reuse

Permissions already exist and are better than what I'd invented: set per group — read-only versus write and delete — with per-tool override, inside the tool's own setup. What's new is everything else. The checks and limits don't live in the tool at all: a guardrail is its own object, built once and applied to as many tools as you like.

Everything that used to be drawn inside the tool pane — data checks, timeouts, rate limits — moved in here, because configuring that per tool means filling the same form nine times and storing nine copies of it. The name is the modal's title, edited in place, so the form opens on the decision rather than on a label.

The scope explanation is a tooltip, not body copy. That's how Skills already does it — the label asks the question, the info icon carries the three-sentence answer. Printing it under the field makes a modal read like documentation, and the people who need it are the ones opening the dropdown anyway.

A guardrail is one check at one point. Where it runs is a single choice, so it's a dropdown: checking what you send to a tool and checking what comes back are different decisions about different payloads, and bundling them into one object makes it vague what you actually switched on. To cover two points you attach the guardrail twice, which also reads better in the library — “Finance check, on Notion, after a tool call” is a concrete thing, where “Finance check, on four hooks” is a configuration you'd have to open to understand.

Which is what separates this from the row in Advanced. They looked like duplicates and they aren't. A guardrail is one attached check; the Sensitive content row in Settings is a standing policy that runs everywhere you tick, which is how Michael described it — “turn on the PII model and a whole bunch of different hooks”. So that one keeps multi-select and this one doesn't, and the difference in control is the difference in meaning.

And what it checks uses the right component for three exclusive options. N8nSegmentControl's own spec says to prefer it over a select or a radio group when there are two to five options and you switch between them immediately.

All tools is the default, and it's the same shape as the Slack access block in section 1. A guardrail you went to the trouble of creating is usually meant to apply, so making you list the tools is work that produces the answer you already had. The deciding case is the one a list gets wrong silently: a tool added next month is covered by all and missed by an enumeration nobody remembers to update. Narrowing stays one toggle away for the guardrail that really is about one slow API.

Two entry points, and they want opposite flows. From a tool you attach one guardrail to one tool, which is the natural move while you're setting that tool up. But the moment you have nine data-table tools, you want the other direction: make the guardrail, then tick the tools it covers — which is why Applies to is in the modal rather than only on the tool. Both exist above. The list itself isn't a new invention — it goes beside Skills in Settings → Context, drawn in the next section.

What a separate object costs. It stops being a setting and becomes a thing with a lifecycle: it can be shared, orphaned, edited from under a tool that depends on it, and deleted. Michael: “when do they stop existing? If they're not in use, does that remove them, or is there somewhere you can actually delete them?” Most of that is already answered — by Skills, which has the same lifecycle and solved it. The next section is that answer. The part it doesn't cover is editing: changing one silently changes every tool using it.

Where guardrails live  Settings → Context, beside Skills

Not the agent's Settings tab — this is n8n's own Settings, outside any agent, which is where the Skills hub already lives. I was going to design it and then found the product has already answered it. Skills is the same problem — a reusable object, made by a builder or imposed by an admin, attached to many agents — and it ships today at Settings → Context with a scope, a usage count and a deletion rule. Every question we had about guardrails has an answer there. So this isn't a new screen, it's a second table.

The scope ladder already exists, and it's three rungs, not one. I'd recommended putting guardrails at project level. That was wrong in shape: Skills doesn't pick a level for you, it asks per object — Global, a named project, or “{agent} only” — and the real tooltip explains it in one line: “A global skill can be added to any agent. A project skill can be added to the agents of that project. An agent skill belongs to one agent.” A guardrail wants exactly the same three, because the admin's PII policy and the one-off back-off for a slow API are both guardrails and belong at different heights.

And it answers Michael's lifecycle question without us designing anything. Skills can't be deleted while they're attached: “Used by 3 agents. Remove the skill from each agent first.” No cascade, no orphans, no silently breaking an agent you can't see. Inherited ones say “You can use but not change this skill”, which is the same read-only state we drew for the PII row in section 3 — arrived at twice, independently, which is a good sign it's right. Moving one between scopes even has its own rule: you need delete permission, because moving removes it from where it is.

Where a guardrail is not like a skill, and it matters. A skill is additive: worst case the agent ignores it and behaves as it would have anyway. A guardrail is subtractive — if it stops applying, something gets out. So the same table carries more risk: editing a Global guardrail changes 12 agents at once, and the delete rule protects the object without protecting the agents from an edit. Skills doesn't need an impact warning before saving. Guardrails probably do, and that's the one screen this pattern doesn't hand us.

Not styled as a warning, on purpose. Editing a shared guardrail is a normal thing to do — it's the reason the object exists. The dialog's job is to make the blast radius visible, not to imply a mistake, which is the same reasoning behind the summary view using grey for an unset rule rather than red. If it nags, people will click through it and it will have cost us a step without buying anything. It only appears when the count is above one.

3 — Cost  nothing to add

I had two new rows here and both are gone. This is the section where the review cut the most, so what's drawn below is the card exactly as it ships today — included so the cuts are legible, not because anything changes.

The card is unchanged, so it's only drawn once — in the assembled Settings view at the end.

Cost cap per operation is out. You can't know what a call costs until it has cost it. Pricing it in advance would mean running the model's own tokenizer over the input first, which is itself a cost, and the output price isn't knowable at all. Michael: “the only way we can know cost about the model is to send it to the model and then it tells us what it costs.” What replaces it isn't in this card: a timeout and a calls-per-minute limit, both in the guardrail object in section 2. Those bound the two things we can actually measure before the fact.

Max runs per hour is out too. Not because it's hard to build — because nobody can set it. A run isn't a unit a builder has a feel for: one message, one session, a sub-agent's work? Two people with long sessions look identical to one runaway loop. The budget already bounds the thing anyone actually cares about, in a unit they understand. Michael: “I would just remove it. The cost cap is the best measurement.”

Which leaves this section with no new control at all — and that's the useful result. Every cost guardrail worth having either already exists here, or turned out to belong to a tool rather than the agent. The one open thread is per-tool override: we're starting with one global setting, and only splitting it per tool if people ask. Michael: “per tool is going to add a lot of configuration that's not going to be used an awful lot.”

A list of categories you type would have been theatre. That was the design, and it dies on one question: what checks it? If the answer is “the model reads the list and tries”, it's the Leave out guidance again with a sterner label, and a label isn't a guarantee. Michael: “I don't think that really makes any difference compared to the leave-out guidance.” A real check has to be deterministic, and memory is the one dimension where that's impossible — it's handed an arbitrary string with no criteria to verify against. So the only honest control is to point at a model trained for the job, and the only category it covers today is PII.

This makes memory guardrails P1, not P0. The P0 line was “things we can check deterministically”, and this falls the other side of it. Worth being explicit rather than shipping the category list as a P0 placeholder that implies a guarantee it can't make.

The model picker is here, and that's what the board asked for. I'd first drawn this as a bare toggle pointing at Advanced, which reads as “someone else decided this” at the exact moment you're deciding it. Martina, on the board: “PII selector — model. The user can select the model that the agent will use to do that.” Same as Sin described it. The cost is that the model can now be chosen in two places, so they have to be one value, not two: pick it here and you've also switched on the before a memory write hook in Advanced. The board's other sticky — “pre-tool call, post-tool call, etc. under Advanced” — is about the hooks, not the model, which is what makes the two compatible.

And it may not be the builder's setting at all. If an admin sets a policy at instance level, the PII toggle here follows the read-only state drawn in section 3 — visible, so nobody designs around a check that's already running, but not editable. The open part is whether instance policies reach accounts without an admin at all.

5 — Output  one row survived, in Settings

I had a card with three rows and a destination list. The card is gone and almost all of it went to the channel — but not quite all. One row is genuinely agent-wide, and it's the one that decides whether people other than the requester can use this agent at all.

Drawn in the assembled Settings view at the end, as the first row of Access and approvals — the card it shares with the approval routing in section 6.

Two options, not three. Ask first looks sensible and can't be built: the approval would have to go to someone in the thread, and Slack can't stop a bystander clicking the button on a request they can see. So the control that enforces who may talk would be approved by whoever happens to be looking. Allow or block.

Where the rest of the dimension went

  1. Specific channels, people and groups — every one of them belongs to a channel, so they're configured there, with the pickers in section 1. Michael: “all the requests we've had so far have been like I want to limit to a Slack user or a Slack channel.”
  2. What the message may contain — the PII check, hooked to before a reply in section 3.
  3. Rules that apply across every channel at once — a real rules engine, and P1. It needs logic rather than a list, since a rule written centrally has to mean something in Slack, Telegram and whatever arrives next.

So the shape is both, not either. I had drawn this as a choice — central panel or channel — and spent a section arguing for one. It's neither: the identities go per channel because that's where they exist and where you're thinking when you set them, and the single rule that's true everywhere goes in Settings because it isn't any channel's business. The mistake was treating “where does this live” as one question when it was really two with different answers.

6 — When it has to ask  in Settings, and it survived intact

Tools set to Ask first, a guardrail that pauses, a sub-agent waiting on approval — all of them need a person. Normally that's whoever is in the conversation. A run started by a schedule has no conversation, so this is the only question none of the other screens can answer.

Also in Access and approvals below, under the reach rule from section 5. Two dimensions, one card, because both come down to which person is on the other end.

Two dropdowns, not one. A flat list of destinations would have to pull every channel's identities into one control. Picking the channel first keeps each lookup inside the integration that owns it, and it's the same shape as the destination picker a guardrail will need. Michael: “it's like a double drop down where you'd pick a channel and then search.”

Three options, and the default is a day. Not five — the small increments don't earn their place, since nobody tunes an approval wait to thirty minutes. A day is the right default because it survives a weekend badly but a night well, and because the alternative defaults are both wrong in one direction: an hour silently kills legitimate work, never stop leaves runs pending past the point the answer means anything.

The two new cards became one, and the merge is the point rather than tidying. Who can talk to it and where it asks for approval look like different subjects — one is permission, the other is routing — but they answer the same question: who is on the other end of this agent. Both only matter because a person is involved, and both are the ones nobody else can answer, since a channel doesn't know who started a run and a tool doesn't know who to interrupt. One card of three rows also survives the junk-drawer test that two cards of one and two rows does not.

Seen whole, the additions are smaller than the tab already is. Sub-agents alone carries five controls and three model pickers; Advanced carries five more. Two new cards of one and two rows, plus one row in Advanced, is not what tipped this tab into being a lot — it was a lot already. That's an argument for the additions and also a warning: the next one genuinely won't fit, and the honest response then is to group rather than stack.

The junk-drawer problem solved itself. I'd argued Settings could carry four new cards as long as each one was a property of the agent. That test was too weak — it would have admitted anything. The review applied a harder one, and it holds better: a rule lives wherever the thing it constrains lives. Identities live in channels. Checks live in a guardrail that can be reused. Only the questions with no other owner are left in Settings: who may talk to the agent at all, who to ask when nobody is there, and which model reads sensitive content. Three rows across three cards, which is a different thing from four cards of controls.

What the summary view costs now. With rules this distributed, a builder has even less chance of seeing the whole picture: channel modals, a guardrail object, two Settings cards. That's the argument for What's bounded — except it's now P1 and moves to publish time, so for the whole of P0 there is no single place to read what an agent is allowed to do. Worth naming as a known gap rather than pretending the distribution is free.

The question the whole page used to hang on is now answered. Sin's doubt on the doc was whether form fields could express any of this: “Could this even be possible — do we want this to be available?” The review answered it both ways. Permissions, limits and routing stay as form fields, because they bound things we can actually measure. Anything about content doesn't — it's a model or a workflow you attach. That split is why the guardrail object exists, and it's the single biggest change on this page.

Deliberately parked. Sandbox command execution (whitelisting, modes, watching for suspicious activity) and network egress are both guardrails and both big enough to derail this. Guardrails on the raw message in and out of the agent — what the current AI Agent node has — are also unplaced; they'd most likely be workflow hooks, but nobody picked a home for them.
