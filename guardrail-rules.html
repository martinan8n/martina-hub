Guardrails — rules & dimensions

Designing the five dimensions from the Dimensions to guardrail an agent doc: where a builder attaches a rule, and how they see what they've actually bounded. Hand-drawn on purpose — none of this is settled. The finished guardrail patterns (cost cap, running states, the trace) live in the Guardrails workstream instead.

🧩 Problem

The rules that bound an agent don't live in one place, and shouldn't: rate limits belong at project or instance level, inbound restrictions on the channel, timeouts in Settings, memory rules attached to persistence, tool permissions per tool. Scattered by design — but that leaves a builder with no way to answer “what is this agent actually allowed to do?” before putting it in production.

Source: Dimensions to guardrail an agent (Notion), plus Sin's comments on it, Oct 4–6
🧪 Hypothesis

If the rules stay where they belong, the thing to design isn't a guardrails panel — it's a readable summary of what's bounded that links out to wherever each rule lives. That's the “foundation we can extend” the doc asks for: adding a dimension later means adding a line to the summary, not redesigning a form.

Open questions

Before this can go further

Raised by the doc, by Sin's comments on it, or by designing against them. Not blockers for the summary view — they are blockers for the dimension screens.

  1. Are guardrail nodes / form fields even viable? Sin, on the doc: “Could this even be possible — do we want this to be available?” The whole authoring mechanism hangs off this. If form fields are out, rules get authored as workflows or by a vendor, and every config screen below changes shape.
  2. What level do rate limits live at? Sin: “could be applicable at the project and instance level” — the doc scopes everything per-agent. Changes whether the summary shows an agent's own rules or inherited ones too, and who can edit them.
  3. What is a memory “persistence guardrail”? Sin wants rules on persistence (e.g. PII via LLMJ), not just preferences. The doc only asks which preferences to expose. These are different products: one is a setting, the other is a rule that can fire.
  4. Reach beyond Slack and Teams. Sin: channel-level enforcement for popular channels, workflow hook as the escape hatch. So what does a builder see for a channel that supports neither — nothing, or a worse-but-present control?
  5. Is the summary read-only? Mine, from designing it. Linking out keeps one source of truth but makes setting five rules a five-screen trip. Editing inline is kinder and immediately forks the truth.
  6. Does “no rule” mean unfinished? An agent with no output rule may be perfectly fine. If the summary styles every gap as a warning, builders will either chase them all or stop reading it.

Trade-off between the two. A is easier to extend — a new dimension is a new row, and it survives the rules living in five different places. Where rules get configured

The summary view only reads. This is the other half: the actual settings, one section per dimension, each sitting where that rule belongs rather than in a guardrails panel. Every control is marked today if it exists in the product now, new if the doc is asking for it, or elsewhere if it belongs on another surface.

3 — Cost & rate  two panels that already exist

Both live in Settings, which renders four cards in this order: Usage and limits, Sub-agent settings, MCP, Advanced. So there are already two homes for a limit, and they behave differently — budget rows open a modal to edit one value, Advanced edits inline. Where a new control goes decides which interaction it inherits, which is the real reason placement matters here.

Why these two ship with a value and the budgets don't. The product already splits this way: technical limits come with a number (max iterations 100, tool concurrency 5, max sub-agents 10), money ones don't. Setting a default budget means deciding what someone else's money is worth, and being too tight cuts legitimate work. These two can carry a default because they can be pitched where no ordinary run reaches them — only a runaway loop or a pathological call does. A guardrail default should be invisible to the people it isn't for. The side effect: a limit that's set because nobody touched it isn't the same as one somebody chose, so the summary view needs to tell those apart rather than showing both as bounded.

And this is where “Not set” stops being a dead end. The budget rows aren't dropdowns — they're buttons with a chevron that open a modal for that one value. So the pattern for setting a limit already exists, and a new limit inherits it for free rather than needing a control invented for it.

What the modal has to answer new

The existing budget modals set an amount and, optionally, an alert before you reach it. A per-operation cap needs a third thing the budget ones don't: what happens to the run when a call is refused. Running out of money and one call being too expensive are different problems, so “top up” is the wrong answer here.

So: Usage and limits, not Advanced. Two reasons, and neither is taste. Everything in Advanced bounds a single execution, while Usage and limits is the only place in the product that bounds anything over time — the monthly budget. And Advanced edits inline, which leaves nowhere to ask the question every one of these limits raises: what happens when it's reached. The budget rows open a modal, which has room for it. Max iterations also carries a schema note — “Do not set unless the user explicitly asks” — so that card is deliberately the quiet corner, and a guardrail people are meant to set doesn't belong in it.

Still per tool new

One thing genuinely doesn't belong in either panel: a cumulative total per source, so an expensive tool can't hide inside an agent-wide figure that still looks fine. That has to sit with the tool, next to its permissions. 4 — Memory  in the Memory card, where the toggle already is

The card that exists today has two rows: Session memory, always on, and a Cross-session toggle. The doc's “named categories” are the Guidance tags from Memory: Configure + Delete, reached from the chevron beside that toggle. The persistence rule is a third thing, and it only makes sense while cross-session is on — so it belongs in the same place, not in a guardrails panel somewhere else.

Why these two sit together and still aren't the same control. Guidance is an instruction; Never store is a check that can refuse. Putting them one under the other, indented under the toggle they both depend on, is the clearest way to show that one is advice and the other is a rule — and that turning cross-session off makes both irrelevant.

5 — Output  the only one with no container to put it in

Every other dimension had somewhere to go: a channel modal, a tool's settings, the Memory card, the budget panel. Output has nothing — the doc calls it “a total gap”, and there is no field anywhere governing where a response may go once generated. So the first decision isn't what the control looks like, it's which surface owns it.

Three candidate homes, none obviously right. Per channel, in the channel modal beside the inbound access step — symmetric and close to where destinations are real, but you'd repeat the rule in every channel. Per agent, in Settings, alongside the other guardrails.* entries — one place, but divorced from the channels it governs. On the tool, since sending is usually a tool call — except “reply to whoever invoked it” isn't a tool call at all. My instinct is Settings, for the same reason the content policy goes there: it's a rule about the agent, not about any one route out. Worth deciding before drawing it properly.

Across three of them — one content policy

The tool checks, the memory rule and the output check all ask the same question: is this content acceptable? Defining that per tool would be unworkable — change what counts as personal data and you'd edit it in a dozen places. It's a property of the agent, so it goes in Settings, where guardrails.budget.* already lives. The enforcement points just switch it on and inherit it.
