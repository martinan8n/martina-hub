Agent summary

One place to read what an agent actually is before you let it out: what it can reach, what it can do, what it spends, what it keeps. Moved out of Guardrails — rules & dimensions on 27 Oct, because it stopped being a guardrails screen the moment it landed at publish time.

🧩 Problem

The rules that bound an agent live in five different places by design — the channel, the tool, a guardrail object, two Settings cards. Each decision is sound on its own, and together they leave a builder with no way to answer the question they actually have before shipping: what is this thing allowed to do?

Source: the guardrails review with Michael, Anne and Sin, 22 Oct 2026
🧪 Hypothesis

A read-only summary, shown when you hit publish, is worth more than a sixth settings panel. It reads what's there rather than storing anything, so adding a dimension later means adding a line, not redesigning a form. The P0 version only reports what we can read — which connections exist and which have a rule attached — and makes no claim about whether an unprotected one is dangerous, because for anything that isn't MCP we can't tell.

Open questions

Before this can go further

Raised on the 22 Oct call, or by designing against it since.

  1. Where does it live between publishes? Publish catches the right moment but it's a modal you dismiss, and the question comes back a week later when you're wondering why the agent didn't post something. It needs a second, permanent entry point — an icon on the agent, a line in the trace, somewhere in Build — and that's undesigned. Martina, on the call: “maybe I want to go back to it later on another day. Where does this live?”
  2. List or path? A is easier to extend and survives the rules living in five places. B teaches the model better and makes a gap land, because it's the end of a line you can follow. Nobody picked.
  3. How do we classify read versus write for non-MCP tools? The whole P1 hangs on it. Offline, on our infrastructure, pre-testable — not in the browser.
  4. Should the assistant be able to analyse an agent's security on demand? Raised by Michael as worth having even once the engine knows about operations. It's a different product from this screen: a conversation rather than a readout.
  5. Does “no rule” mean unfinished? An agent with no content check may be perfectly fine. If every gap is styled as a warning, builders either chase them all or stop reading.
  6. Could it be prose instead? Martina, on the call: “this can be in this way, or this can be text like a paragraph explaining what the agent does.” A sentence a person can check is a different product from a table, and it's the version an LLM could write.
  7. It reads state we haven't built yet. Guardrails, the content policy and per-channel access all have to exist before there's anything to report.

The publish flow

Hitting Publish is the one moment a builder is deciding whether this agent is safe to let out, so it's where the summary goes. Two steps: read what it's allowed to do, then confirm. Step 2 already exists in the product and keeps everything it carries today. Same agent throughout — a weekly metrics sync that posts to Slack.

P1, and not in Settings. It gets built after the permissions it summarises. Michael: “I think it would be cool to have a place where you can see all the permissions, but I don't think it's a P0.” Martina and Anne, on the call: “this doesn't belong in the settings. Idea: when you hit Publish.”

Revised after the thread on 27–28 Oct, and the change is bigger than it looks. Every row now states a fact we can read rather than a property we'd be asserting. “Nothing destructive runs without asking” is gone, because we can't say it. Michael: “we really can't make a guarantee like that, we don't actually know 100% what is destructive and what isn't — could just say what requires approval and what doesn't.” So it says 9 run without asking, 3 ask first. Same information, no promise attached.

The limit underneath it. We only know read versus write for MCP tools, where the server declares it. A workflow tool or a node tool is opaque — it may delete a table or read a row and we can't tell which. So a summary that sorted tools into safe and dangerous would be guessing on most of them, and guessing in the direction that makes people relax.

Explicit states, without warning highlights. Public access and tools that run without approval may be intentional. Each row states the current configuration in plain language; a missing limit or content check is reported directly, without implying that it is unsafe.

P0 lite, P1 analysed

Agreed in the thread by Sin and Michael. This screen is the P0.

  1. P0 — what we can read. Connections grouped by dimension, with rules attached or not. No classification, no judgement, nothing we'd have to be right about.
  2. P1 — classify the operations. Work out read versus write for non-MCP tools and build a schema, so the summary can flag a write with no rule on it. Sin's framing: do it offline so it's pre-testable and doesn't burn credits on every view.
  3. Also raised, and parked: letting the assistant analyse the agent's security on demand, and generating this view with generative UI. Michael wants the ask-the-assistant option even after engine v2 adds operation awareness.

One caution on the P1 that's worth keeping visible. Offline has to mean our infrastructure, not the user's browser. Michael: WebLLM-style in-browser models are “a massive download”, most enterprise hardware can't run them, and “trusting risk analysis to the smallest least capable models on the market might not be the safest bet”. A wrong classification here is worse than none, because it tells someone they're covered when they aren't.

Publish answers when, not where. Showing this before you publish catches the one moment a builder is receptive to it. But it's a modal you dismiss, and the question comes back a week later when you're wondering why the agent didn't post something. So it needs a second, permanent entry point — an icon on the agent, a line in the trace, somewhere in Build — and that's undesigned. Putting it in Build was the first instinct and it clutters a page that's already full.

Step 2 — Agent published  exists today, unchanged

Whichever option step 1 uses, confirming lands here. This modal already ships, so the summary has to sit before it rather than replace it — everything it carries is still needed.

Agent published

Your agent is now published and ready to use.

You can talk to it in n8n Chat now. Make it available when your project should have it too.

Any changes you make to this agent will not be published until you publish it again.

Don't show again Got it Talk to agent

The checkbox is the problem this flow inherits. Don't show again writes to localStorage, so whoever publishes most is the first to silence step 2 — and if the summary gets folded into the same modal, they silence that too. The summary is the one screen you don't want dismissable for the people shipping the most agents, which argues for keeping the two steps separate: step 1 always shows, step 2 stays skippable.

And rollback reuses this modal. Restoring an old version publishes it, so a builder lands on “Agent published” for an agent that was already live. If step 1 runs there too it's arguably more useful than at first publish — you're reinstating rules you may not remember — but “you can talk to it in n8n Chat now” reads oddly when it already could.

Memory came out of the summary. It was the one row with no rule to report — “remembers across sessions, no rule on what it may keep” is a fact about the product, not about this agent, and it will stay that way until the PII check ships as P1. A summary row that reads the same for every agent teaches nobody anything, and four rows that all say something beats five where one is filler.

Both takes assume the rules exist. Every pill above reads a state we haven't built yet. If this ships before the permissions it summarises, it summarises nothing — which is exactly the argument for it being P1, and the reason it's drawn here rather than queued.

Needs attention

The same summary idea at the other end of the agent's life. Finish setup already ships in the Build tab: a progress wheel and a popover of tasks, which empties as you build and then says Done! This asks what that control does on day thirty, when nothing is unfinished but something is wrong.

Finish setup, at the top of Build today new shape

A light violet panel above the first card, with the tasks in it — rather than a pill in the corner that hides them behind a popover. No border, no icons, no count: a heading in the accent colour and a list. Outstanding first, done ones struck through. The six tasks and their order are the real ones from the registry; Add channels is written but switched off behind a TODO, and Publish agent appears once the agent has been tested.

Why in the page rather than in the corner. The pill is the smallest possible version of this and it has one cost: the tasks are invisible until you click. For the thing whose entire job is to tell a half-built agent what it still needs, hiding the list behind a hover is backwards — and the trigger's label never counted down anyway, so the corner gave you no information at all until opened. In the page, the next action is readable without a click and sits where the eye already starts.

What it costs, and why there's no dismiss. Vertical space at the top of a tab that is already long. It earns that by disappearing on its own: setup tasks complete and the panel goes, problems get fixed and the panel goes. A dismiss would only let someone hide a thing that is still true, which is how a banner turns into noise people learn to skip.

One panel, two reasons to appear, and they never overlap. Setup is finite and one-way: every task is a door that closes behind you, which is why a progress wheel works. Attention is recurring — a credential expires, a budget fills — and would make that same wheel run backwards. Reusing the position, the colour and the anatomy means a builder learns one place to look; the heading and the rows say which kind of problem it is. Writing each row as the action rather than the symptom — Reconnect Notion, not Notion credential expired — also makes the two panels read the same way: a list of things to do.

Every row has to be actionable from Build. An expired credential, a budget nearly spent, unpublished changes, a tool failing every run — all fixable from here, so all earn the space. A single failed execution doesn't; that belongs in Sessions. Put run-level noise in this panel and it turns into a notification feed, which is how this pattern usually dies.

Open

  1. Does it belong to Build at all? Setup is a Build activity; a spent budget isn't, and neither is an expired credential shared across agents. The trigger is in the Build header, so the surface argues for Build — but the problems may be read more often from the Agents list, where you'd see them across every agent at once.
  2. Add channels is written and hidden — getVisible: () => false with a TODO in the registry. Worth deciding, since a published agent with no channel is reachable by nobody, which is exactly the kind of thing this control exists to catch.
  3. Does attention outrank setup, always? Drawn that way. An agent that was never finished and now also has a dead credential shows the alert, and the half-built state is one click away rather than on the face of it.
