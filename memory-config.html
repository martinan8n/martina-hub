Memory: Configure + Delete

Episodic memory works today, but it's opaque and non-configurable — builders can't shape what an agent remembers, and can't reliably delete what it stored. This prototype covers the three user-facing surfaces Phase 1 adds on top of today's Session memory / Cross-session memory settings.

🧩 Problem

Builders who don't trust or can't tune what gets captured resort to workarounds — manual system-prompt instructions, or a hand-built external store that bypasses the native pipeline entirely. And today's dedup behavior means a naive delete could leave a duplicate resurfacing later — a real problem if delete is ever used to satisfy an erasure request.

🧪 Hypothesis

Three additive surfaces on the same underlying data close both gaps: an editable guidance field (paired with a read-only sample, so people aren't tuning blind), inline-in-trace delete grounded in a builder-facing audit log, and a plain standalone list for proactive cleanup. None of this replaces or redesigns today's capture/recall behavior.

Build → Knowledge: memory relocated (grounded in real Build/Knowledge screenshots, Oct 16)

Per the Build/Knowledge split we landed on: the memory configuration (Session/Cross-session toggle, Guidance) stays in Build, same as today — it's a behavior setting, not content. The stored memories themselves move to Knowledge as a new card, since they're content the agent knows, the same category as uploaded files and vector stores. Shows the last 10 inline; “View all” opens a filterable full list (by user, by channel) with delete — this is also where Recently captured and Manage memory converge into one list at two zoom levels, instead of staying separate surfaces.
