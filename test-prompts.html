Test scenarios

Opening the Test panel on a new agent gives you an empty chat and a cursor. The hardest part of testing an agent is the first message — you wrote the instructions, so you already know what it does, and that's exactly why nothing comes to mind. This offers to write a few.

🧩 Problem

Test agent is one of the six Finish setup tasks, and it's the one with nothing behind it. The other five hand you a picker or a field; this one hands you a blank composer and the placeholder “Type a message…”. A builder who can't think of an example doesn't test, and an agent that was never tested gets published anyway.

Source: agentSetupTasks registry, and the empty state of the preview panel
🧪 Hypothesis

The agent's own instructions already describe what it should handle, so the examples can be written from them. Offering rather than auto-filling keeps the panel quiet for people who know what they want to type, and the product already does this twice — evals generates test cases from the instructions, and chat agents carry suggested prompts.

Open questions

Before this can go further

  1. Offer, or just write them? Drawn as an offer, so the panel stays quiet for someone who already knows what to type. The argument the other way is that a button between you and the examples is one more thing to click when the whole point is removing friction.
  2. What happens to a scenario once used? It could vanish, grey out, or stay. If they stay, the second message is as easy as the first; if they vanish, the panel empties out and you're back where you started.
  3. Does this overlap with evals? Generate test cases already writes examples from the instructions, and the preview flow already runs one and saves it as a check. This is the same generator with a different purpose — try it once, versus keep it as a test. Worth deciding whether running a scenario should offer to save it as a check.
  4. Agents with no instructions yet. The generator has nothing to read. Either the offer doesn't appear, or it reads the tools instead, which gives much vaguer examples.
  5. Who writes them — and what does that cost? A model call on opening a panel, for every agent, whether or not anyone uses the scenarios. Offering rather than auto-generating also solves that.

Test scenarios, not examples, and the word does work. Examples describes the format — here are some messages. Test scenarios describes the job: each one is a case you're running the agent against, which is why a bad answer is information rather than a disappointment. It also matches the vocabulary already next door, where evals calls its generated cases test cases. Plain scenarios would have overpromised — that implies a situation with context, and these are single messages — but test scenario is a case, which is exactly what they are.

The button carries the assistant's own mark. Not a generic sparkle — the real AssistantIcon, the four-pointed burst with its violet-to-orange gradient, which is the same mark used on the Ask Assistant button and avatar. It matters more than decoration here: it's the thing that says a model is about to write this, which sets the expectation that the examples are generated rather than canned, and that they'll differ per agent.

“Practice run. Nothing is sent, saved or changed.” Lifted verbatim from the preview flow, and it's load-bearing here rather than decorative. This agent posts to Slack. Without that line the first thing a builder weighs is whether testing will message a real channel, and the safe move is not to test.

The wait says what it's reading. Reading the instructions and writing scenarios rather than a bare spinner, because it sets up why the examples are relevant when they arrive — and because a builder who sees it and gets poor examples knows immediately that the instructions are the thing to fix.

3 — The scenarios

Test agent
Select a scenario to test the agent against, or write your own below.
Summarise the tickets that came in this morning
What are people complaining about most this week?
Post today's ticket summary to #customer-support
Which tickets has nobody replied to yet?
Write different scenarios
Practice run. Nothing is sent, saved or changed.
Test Metrics Sync…

Four, not one, and not ten. One example tests one path and tells you nothing about the rest; ten is a wall of text in a narrow panel. Four fits without scrolling and covers different shapes of request — a summary, an analysis, an action that writes somewhere, and a gap-finding question. The fourth is the useful one: it's the kind of request builders don't think to try and agents most often get wrong.

They're written from the instructions, which makes them a test of the instructions too. If the generator produces something the agent obviously can't do, the instructions promise something the tools don't deliver — and that's worth knowing before publishing. The same generator already exists for evals: “Draft a few realistic requests from your agent's own instructions”.

Written as messages, not as topics. “Which tickets has nobody replied to yet?” rather than “Unanswered tickets”. A topic makes you compose the sentence yourself, which is the work we're trying to remove; a full message can be sent with one click and shows the builder the register real users will write in.
